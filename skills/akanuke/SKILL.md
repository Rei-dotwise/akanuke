# akanuke

AIで作った資料や文章は、内容が正しくても、型の使い方でAIが作ったと分かってしまう。キーメッセージを体言止めで決める、何でもカギカッコで囲む、番号と縦線と補足文をセットで置く、同じラベルを3回繰り返す、といった型だ。書くときはこれらの型を避け、書いた後は残った型を見つけて抜く。このスキルはその両方に使う。

## 前提にする考え方

型そのものが悪いわけではない。番号や色や縦線も、意味があれば使ってよい。意味がないのに置かれた型が、AIっぽく見える。だから直すときは、消すか意味を持たせるかのどちらかを選ぶ。消して空いた場所を、別の飾りで埋めない。

読み手は一つずつの表現より、型が重なったときにAIだと気づく。1か所の体言止めは問題にならないが、見出しも小見出しも結論もすべて体言止めなら目立つ。

AIにセルフレビューを頼んでも、これらの型はあまり指摘されない。そのため、目視の前に機械で候補を洗い出し、判断だけを文脈で行う。

このスキルに書いた回数（体言止めは1〜2か所まで、など）は見直すきっかけであり、上限ではない。残すか直すかは、読み手への影響で決める。見出しを続けて読むと同じ調子が続く、太字が多くて最初に読む箇所を選べない、といった影響が出ているなら直す。

## 迷ったときの三つの問い

個別のパターンに当てはまるか分からないときは、次の三つで見直す。どれかに引っかかったら、その箇所を直すか、残す理由を言えるかを確かめる。

1. なぜここに、と聞かれて答えられるか。「なぜグレー？」「このカギカッコの意味は？」「この番号はなぜ2桁？」と聞かれて答えられない飾りは外す。
2. 別の会社の資料に貼っても通じるか。「価値を最大化する」のように、社名やテーマを入れ替えても成り立ち、しかも誰が何をするのかも分からない文は、何も言っていない。対象、行動、数字のどれかを入れる。
3. 会議で声に出して言えるか。人が口頭で言わない言い回し（「変わるのは、営業の質だ」）は、書き言葉としても浮いている。ただし、操作手順、契約上の注記、表の項目のように、もともと口頭で読み上げない文には当てはめない。

## 使い方

依頼に合わせて、次の三つのどれかで動く。指定がなければ、新しく書く依頼なら「書く」、既存の文面があれば「直す」を選ぶ。

- 書く: 「書く前に決めること」と「書くときに避けること」を守って書き、書き終えたら「直す」の手順で点検する。
- 直す: 該当箇所を見つけて直した版を出す。直した箇所が多いときは、主な変更を3〜5行で添える。
- 指摘だけ: 本文は書き換えず、箇所、パターン名、AIっぽく見える理由、直し方の案を一覧で返す。

対象に合う行のファイルをすべて読む。直す前と直した後の具体例は `references/examples.md` にある。迷ったら該当する例を読む。

| 対象 | 読むファイル |
|---|---|
| スライド、提案書、1枚資料、図解 | `references/sentences.md`、`references/slides.md` |
| note、ブログ、メルマガ | `references/sentences.md`、`references/note-and-x.md` |
| X、Threads、短い返信、プロフィール文 | `references/sentences.md`、`references/note-and-x.md` |
| メール、レポート、社内文書 | `references/sentences.md` |

## 機械で候補を出す

手元に .md / .txt / .pptx のファイルがある場合は、目視の前に検出スクリプトを回す。Python 3.9 以上の標準ライブラリだけで動き、テキストは UTF-8（読めなければ CP932）で読む。PDF や、チャットに貼られただけの文章には使わず、参照ファイルを当てて目視で点検する。

```
python3 <このスキルのフォルダ>/scripts/check.py <ファイル>
python3 <このスキルのフォルダ>/scripts/check.py --json <ファイル>
```

pptx では、文の型に加えて、同じラベルの繰り返し、0付き番号、文字の左にある細い縦長の図形、水平の区切り線、塗り色の数、小さい文字の長い注釈、1枚の文字量を数える。スライド番号は表示順で、体言止めや説教調の反復はデッキ全体で数える。体言止めは「。」で終わる文だけが対象で、句点のない見出しは目視で見る。検出は候補であり、全部直せという指示ではない。一つずつ、直すか、理由があって残すかを決める。

スクリプトでは分からないものもある。改行位置、色の意味、要素同士の関係、タイトルと中身のずれは、資料を画像で見て確認する。画像が見られない環境なら、確認していないことを報告に書く。

## 書く前に決めること

AIっぽさの多くは、書く前の設計を飛ばしたことから生まれる。言いたいことが決まっていないと、AIは網羅と装飾で埋めようとする。

1. 読み手は誰で、読んだ後に何をしてほしいのかを一文で書く。
2. スライドなら、1枚で伝えることを一文に絞る。二つ以上あるなら枚数を増やす。
3. 見出しやタイトルは、それだけ読めば中身が分かる文にする。「〜について」「〜の概要」で済ませない。
4. 並べる要素同士の関係（順番なのか、比較なのか、原因と結果なのか）を決めてから配置する。関係を言えない要素は並べない。

## 書くときに避けること

参照ファイルを読む前でも、少なくとも次の型は意味なく使わない。どこまで許すかは各参照ファイルに書いてある。

- キーメッセージや見出しを、体言止め、「〜のは、〜。」の溜め、「〜ではなく〜」で繰り返し決める
- 引用でも定義でもない語をカギカッコで囲む
- 「効く」「刺さる」「最大化」「シームレス」のように、何が起きるのかを書かない語
- 中身の数より先に「3つ」と決めて並べる
- 「結論：」「【基本方針】」のラベル見出し、「いかがでしたか」の締め
- スライドの01番号、左の縦線、同じラベルの繰り返し、意味のない色分け、長い免責注釈

## 直すときの順番

細かい表現から直すと、構造の問題が残ったまま磨くことになる。次の順で見る。

1. 構造: 1枚または1記事に詰め込みすぎていないか。タイトルと中身が合っているか。同じ情報を2回言っていないか。
2. 飾り: 番号、縦線、色、カギカッコ、太字、アイコンに意味があるか。
3. 文: 体言止め、「〜のは、〜。」の溜め、「〜ではなく〜」、決め台詞、空疎な語。
4. 仕上げ: 改行位置、注釈の長さ、余白。

修正版を .md / .txt / .pptx で保存した場合は、検出スクリプトをもう一度回し、新しい候補が出ていないかを見る。最後に三つの問いで全体を通して読む。

## 直した後に出やすい新しい型

AIっぽさを抜こうとすると、AIは別の型に入りやすい。直した版に次のものが出ていたら、それも直す。

- くだけた感じの演出: 「正直、」「ぶっちゃけ」「〜なんですよね」「（笑）」「めっちゃ」を、書き手の普段の口調と関係なく足す。
- 作った体験: 「自分も最初は失敗しました」のような失敗談や感情を、書き手から聞かずに足す。
- 一律の短文化: 全部の文を短く切り、リズムが単調になる。長い文と短い文は混ざっていてよい。
- 同じ直し方の繰り返し: 全部の見出しを問いの形にする、全部の段落を体験から始める。新しい型が一つ増えただけになる。

## 直しすぎに注意する

- 体言止めや箇条書きは、数を減らせばよい。全部なくすと、今度は間延びした文になる。
- 具体が足りないときは、書き手に聞くか「要確認」と書く。体験、感情、数字を作り足さない。まず元の文にある内容だけで直し、それで足りないときに書き手へ聞く。
- 元の文書の濃淡を残す。重要な節は厚く、補足の節は薄いままでよい。
- 事実、数値、固有名詞、約束事項は変えない。数値は「約」などの幅と、目標か実績か、誰の数字かも含めて変えない。表現を変えた結果、意味が変わっていないかを最後に確認する。

## 指摘だけのときの出し方

パターン名は、参照ファイルの見出しと同じ名前を使う。

```
| 箇所 | パターン | AIっぽく見える理由 | 直し方の案 |
|---|---|---|---|
| タイトル | タイトルが中身と合っていない | 進め方（共有）と確認事項（判断）を一つのタイトルに並べている | 決めてほしいことを一つ、問いの形で書く |
```

件数が多いときは、読み手が最初に気づく順（タイトル、キーメッセージ、目立つ装飾、本文、注釈）に並べる。
