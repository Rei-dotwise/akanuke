# akanuke

AIで作った資料や文章は、内容が合っていても、型の使い方でAIが作ったと一目で分かる。例えば次のような型だ。

- キーメッセージを体言止めで決める
- 何でもカギカッコで囲む
- 番号と縦線と補足文をセットで置く
- メールに見出しと太字を付け、締めの挨拶を三つ重ねる

このスキルでは、書くときにこれらの型を避け、書いた後に残った型を見つけて抜く。対象は、メール、資料、トークスクリプトのように、ビジネス職が毎日書く文章である。

## 依頼に名前がないとき

日本語のビジネス文書を書く・直す依頼なら、「akanuke」と言われなくても、このスキルの手順で書く。そのときは、手順を使ったことや点検の過程を本文の前後に書かず、仕上がった文面を出す。既存の文面を直した箇所が多いときだけ、主な変更を文面の後に短く添える。指摘の表は、点検やレビューを頼まれたときだけ出す。

コード、設定ファイル、英語の文書、note・ブログなどの記事、XなどのSNS投稿、小説は対象にしない。

## 前提にする考え方

型そのものが悪いわけではない。番号や色や縦線も、意味があれば使ってよい。意味がないのに置かれた型が、AIっぽく見える。だから直すときは、消すか意味を持たせるかのどちらかを選ぶ。消して空いた場所を、別の飾りで埋めない。

型は一つずつより、重なったときに目立つ。1か所の体言止めは問題にならないが、見出しも小見出しも結論も体言止めだと、続けて読んだときに同じ語尾が並ぶ。

ビジネスの定型は抜かない。「お世話になっております」「ご確認のほど、よろしくお願いいたします」のように、相手も使っていて期待している挨拶は、そのまま残す。AIが定型に上乗せした分だけを抜く。

AIにセルフレビューを頼んでも、これらの型はあまり指摘されない。そのため、目視の前に機械で候補を洗い出し、判断だけを文脈で行う。

このスキルに書いた回数（体言止めは1〜2か所まで、など）は見直すきっかけであり、上限ではない。残すか直すかは、読み手への影響で決める。見出しを続けて読むと同じ調子が続く、太字が多くて最初に読む箇所を選べない、といった影響が出ているなら直す。

## 迷ったときの三つの問い

個別のパターンに当てはまるか分からないときは、次の三つで見直す。どれかに引っかかったら、その箇所を直すか、残す理由を言えるかを確かめる。

1. なぜここに、と聞かれて答えられるか。「なぜグレー？」「このカギカッコの意味は？」「この番号はなぜ2桁？」と聞かれて答えられない飾りは外す。
2. 別の会社の資料に貼っても通じるか。「価値を最大化する」のように、社名やテーマを入れ替えても成り立ち、しかも誰が何をするのかも分からない文は、何も言っていない。対象、行動、数字のどれかを入れる。
3. 会議で声に出して言えるか。人が口頭で言わない言い回し（「変わるのは、営業の質だ」）は、書き言葉としても浮いている。ただし、操作手順、契約上の注記、表の項目のように、もともと口頭で読み上げない文には当てはめない。

## 使い方

依頼に合わせて、次の三つのどれかで動く。指定がなければ、新しく書く依頼なら「書く」、既存の文面があれば「直す」を選ぶ。

- 書く: 「書く前に決めること」と「書くときに避けること」を守って書き、書き終えたら「直す」の手順で点検する。
- 直す: 該当箇所を見つけて直した版を出す。直した箇所が多いときは、主な変更を3〜5行で添える。
- 指摘だけ: 本文は書き換えず、箇所、パターン名、AIっぽく見える理由、直し方の案を一覧で返す。

対象に合う行のファイルをすべて読む。直す前と直した後の具体例は `references/examples.md` にある。迷ったら該当する例を読む。

| 対象 | 読むファイル |
|---|---|
| スライド、提案書、1枚資料、図解 | `references/sentences.md`、`references/slides.md` |
| メール、チャット、社内連絡 | `references/sentences.md`、`references/email.md` |
| トークスクリプト、商談・電話・デモの台本、プレゼンの読み原稿 | `references/sentences.md`、`references/talk-script.md` |
| 報告書、議事録、社内文書 | `references/sentences.md` |

AIの出力を貼り付けて使うときは、`references/sentences.md` の「AIの出力をそのまま使うと残るもの」も見る。

## 機械で候補を出す

手元に .md / .txt / .pptx のファイルがある場合は、目視の前に検出スクリプトを回す。Python 3.9 以上の標準ライブラリだけで動き、テキストは UTF-8（読めなければ CP932）で読む。PDF や、チャットに貼られただけの文章には使わず、参照ファイルを当てて目視で点検する。

```
python3 <このスキルのフォルダ>/scripts/check.py <ファイル>
python3 <このスキルのフォルダ>/scripts/check.py --json <ファイル>
python3 <このスキルのフォルダ>/scripts/check.py --script <台本のファイル>
```

`--script` はトークスクリプトや読み原稿に付ける。1文の長さと、声に出すと硬い書き言葉も数える。

pptx では、文の型に加えて、同じラベルの繰り返し、0付き番号、文字の左にある細い縦長の図形、水平の区切り線、塗りの指定の数、小さい文字の長い注釈、1枚の文字量を数える。スライド番号は表示順で、体言止めや説教調の反復はデッキ全体で数える。体言止めは「。」で終わる文だけが対象で、句点のない見出しは目視で見る。「12件。」「1200万円。」「三件。」のように、数字のあとに単位が続いて終わる報告は数えない。出力の「図形の確認」は参照ファイルにない参考情報で、文字の左にない細い図形を、位置と役割を画像で確かめる候補として挙げたものである。

検出は候補であり、全部直せという指示ではない。一つずつ、直すか、理由があって残すかを決める。「警告」が出た語でも、その文脈で最も短く正確な言い方なら残してよい。採否は、文脈と読み手の負担で決める。

スクリプトでは分からないものもある。改行位置、色の意味、要素同士の関係、タイトルと中身のずれは、資料を画像で見て確認する。画像が見られない環境なら、確認していないことを報告に書く。

## 書く前に決めること

AIっぽさの多くは、書く前の設計を飛ばしたことから生まれる。言いたいことが決まっていないと、網羅と装飾で紙面が埋まりやすい。

1. 読み手は誰で、読んだ後に何をしてほしいのかを一文で書く。
2. メールなら、用件を件名と最初の2行で言えるようにする。スライドなら、1枚で伝えることを一文に絞る。二つ以上あるなら枚数を増やす。
3. 見出しやタイトルは、それだけ読めば中身が分かる文にする。「〜について」「〜の概要」で済ませない。
4. 並べる要素同士の関係（順番なのか、比較なのか、原因と結果なのか）を決めてから配置する。関係を言えない要素は並べない。
5. 台本なら、相手が答える場所と、答えによって次に話すことが変わる場所を先に決める。

## 書くときに避けること

参照ファイルを読む前でも、少なくとも次の型は意味なく使わない。どこまで許すかは各参照ファイルに書いてある。

- キーメッセージや見出しを、体言止め、「〜のは、〜。」の溜め、「〜ではなく〜」で繰り返し決める
- 引用でも定義でもない語をカギカッコで囲む
- 「効く」「刺さる」「最大化」「シームレス」のように、何が起きるのかを書かない語
- 中身の数より先に「3つ」と決めて並べる
- 「結論：」「【基本方針】」のラベル見出し
- スライドの01番号、左の縦線、同じラベルの繰り返し、意味のない色分け、長い免責注釈
- メールの見出しと太字、定型の前置きと締めの重ね
- 台本の長い一文と、相手が都合よく納得するせりふ

## 直すときの順番

細かい表現から直すと、構造の問題が残ったまま磨くことになる。次の順で見る。

1. 構造: 1通、1枚、1場面に詰め込みすぎていないか。タイトルや件名と中身が合っているか。同じ情報を2回言っていないか。
2. 飾り: 番号、縦線、色、カギカッコ、太字、アイコン、見出しに意味があるか。
3. 文: 体言止め、「〜のは、〜。」の溜め、「〜ではなく〜」、決め台詞、空疎な語、敬語の重ね。
4. 仕上げ: 改行位置、注釈の長さ、余白。

修正版を .md / .txt / .pptx で保存した場合は、検出スクリプトをもう一度回し、新しい候補が出ていないかを見る。

直す前と直した後をテキストで保存できる場合は、前後比較のスクリプトも回す。チャットで受け取った文面でも、作業用の一時フォルダに2つのファイルとして書き出して比べる。

```
python3 <このスキルのフォルダ>/scripts/diff.py --year <年> <直す前> <直した後>
```

数値と「約」などの幅、日付・曜日・時刻、否定の数、文の立場（依頼、提案、相談、決定、見込み、目標）、条件の語（以外、場合、のみ）の変化を「恐れ」として挙げる。「恐れ」が出たら、その箇所を原文と並べ、意味を変えてよい理由がなければ戻す。文書全体で語を数える仕組みなので、何も出なくても意味が同じとは限らない。

最後に三つの問いで全体を通して読む。

## 直した後に出やすい新しい型

AIっぽさを抜こうとすると、AIは別の型に入りやすい。直した版に次のものが出ていたら、それも直す。

- くだけた感じの演出: 「正直、」「ぶっちゃけ」「〜なんですよね」「（笑）」を、書き手の普段の口調や相手との関係と関係なく足す。
- 作った体験: 「弊社でも最初は失敗しました」のような失敗談や感情、導入事例を、書き手から聞かずに足す。
- 一律の短文化: 全部の文を短く切り、リズムが単調になる。長い文と短い文は混ざっていてよい。
- 同じ直し方の繰り返し: 全部の見出しを問いの形にする、全部のメールを同じ書き出しにする。新しい型が一つ増えただけになる。

## 直しすぎに注意する

- 体言止めや箇条書きは、数を減らせばよい。全部なくすと、今度は間延びした文になる。
- 具体が足りないときは、書き手に聞くか「要確認」と書く。体験、感情、数字、事例を作り足さない。まず元の文にある内容だけで直し、それで足りないときに書き手へ聞く。
- 元の文書の濃淡を残す。重要な節は厚く、補足の節は薄いままでよい。
- 事実、数値、固有名詞、日時、約束事項は変えない。数値は「約」などの幅と、目標か実績か、誰の数字かも含めて変えない。依頼か報告か、提案か相談か、決定か未決か、という文の立場と、元の文にある条件も変えない。表現を変えた結果、意味が変わっていないかを最後に原文と並べて確かめる。
- 相手との関係で決まる丁寧さは下げない。社外の目上の相手に、社内チャットの調子で書かない。

## 書き手の文体に寄せる

AIっぽさを抜いたら、書き手の文体に寄せて仕上げる。書き手が過去に送ったメールや資料が手元にあれば、挨拶の言い回し、一文の長さ、敬語の強さを確かめる。書き手が「この言い方はしない」と指摘した表現は、同じ作業の中では使わない。継続して避けたい場合は、書き手が指定した文体メモやプロジェクトの指示ファイルに残すよう提案する。

別のモデルの出力や他人の下書きから、うまい言い回しを取り入れるときも、事実、数値、書き手の立場は変えない。

## 指摘だけのときの出し方

パターン名は、参照ファイルの見出しと同じ名前を使う。

```
| 箇所 | パターン | AIっぽく見える理由 | 直し方の案 |
|---|---|---|---|
| タイトル | タイトルが中身と合っていない | 進め方（共有）と確認事項（判断）を一つのタイトルに並べている | 決めてほしいことを一つ、問いの形で書く |
```

件数が多いときは、読み手が最初に気づく順（件名やタイトル、キーメッセージ、目立つ装飾、本文、注釈）に並べる。
